## Phase 2: Foundational (Blocking Prerequisites)

**Purpose**: The config reader and the `Database` type that every client and the check script use

**⚠️ CRITICAL**: No user story work can begin until this phase is complete

- [x] T004 Create `lib/supabase/config.ts` with no imports, exporting `type SupabaseConfig = { ok: true; url: string; publishableKey: string } | { ok: false; missing: string[]; invalid: string[] }` and `readSupabaseConfig(): SupabaseConfig`. Read values with static access `process.env.NEXT_PUBLIC_SUPABASE_URL` and `process.env.NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (no dynamic lookup, so Next.js can inline them). Rules from data-model.md, verbatim: "`NEXT_PUBLIC_SUPABASE_URL` MUST parse as an absolute `http:` or `https:` URL (`http` allowed only for `localhost`/`127.0.0.1`, i.e. the local stack). ## Phase 3: User Story 1 - The portal can talk to the backend (Priority: P1) 🎯 MVP

**Goal**: Server and browser code each have one entry point to Supabase, and a developer can confirm that the connection works.

**Independent Test**: With valid settings in `.env`, `npm run db:check` prints success and exits 0. Every existing screen looks and behaves as before (quickstart Scenarios 1 and 3).

- [x] T006 [P] [US1] Create `lib/supabase/server.ts` starting with `import "server-only"`, exporting `getServerSupabase(): SupabaseClient<Database> | null`. It calls `readSupabaseConfig()` and returns `null` when `ok` is false. Otherwise it returns `createClient<Database>(url, publishableKey, { auth: { persistSession: false, autoRefreshToken: false, detectSessionInUrl: false } })` from `@supabase/supabase-js`, creating a new stateless client per call. It MUST NOT import `next/headers`, call `cookies()`/`headers()`, or use `createServerClient` from `@supabase/ssr` (FR-008). Add a short comment noting that the cookie-based server client and `proxy.ts` belong to the future sessions feature.
- [x] T007 [P] [US1] Create `lib/supabase/client.ts` exporting `getBrowserSupabase(): SupabaseClient<Database> | null`. It returns `null` when `typeof window === "undefined"` (never created during server render) or when `readSupabaseConfig()` is not ok. Otherwise it lazily creates and caches one module-level `createBrowserClient<Database>(url, publishableKey)` from `@supabase/ssr` and returns the same instance on later calls. Do not add `"use client"` to this module: it is a plain module imported by client components.
- [x] T008 [US1] Create `scripts/db-check.ts` per `contracts/db-check-cli.md`. Import `readSupabaseConfig` from `../lib/supabase/config.ts`. If the config is not ok, print to stderr `✗ Falta configuración: <missing/invalid names joined by ", ">. Revisa .env (ver .env.template).` and exit 2. Otherwise run `fetch(`${url}/auth/v1/health`, { headers: { apikey: publishableKey }, signal: AbortSignal.timeout(5000) })` with these outcomes:
  - Network, DNS or timeout error, or HTTP 5xx: print `✗ No se puede alcanzar Supabase en <url>: <motivo>` and exit 3.
  - HTTP 401 or 403: print `✗ Supabase rechazó la clave publicable (HTTP <code>).` and exit 4.
  - HTTP 2xx: print `✓ Conectado a Supabase (<url>)` to stdout and exit 0.
  - Any other status: print `✗ Respuesta inesperada de Supabase (HTTP <code>).` and exit 1.
    Never print key values. Use only syntax that Node 24's type stripping accepts: no enums, no namespaces, no parameter properties.
- [x] T009 [US1] Add `"db:check": "node --env-file-if-exists=.env scripts/db-check.ts"` to `scripts` in `package.json`
- [x] T010 [US1] Verify US1 with quickstart Scenario 1 (`npm run db:check` exits 0 against the remote project) and Scenario 3 step 3 (home, `/juegos`, a detail page, `/juegos/<slug>/jugar` and `/rankings` unchanged at 390 px and 1440 px). Confirm that no file outside `lib/supabase/` and `scripts/` imports `@supabase/supabase-js` or `@supabase/ssr` (`grep -rn "@supabase/" app components lib --include=*.ts --include=*.tsx`).

**Checkpoint**: The connection works and screens are unchanged. This is the MVP.

## Implementation notes

- T001: `server-only` was installed as a runtime dependency, not a dev dependency, so production
  builds that skip devDependencies still resolve it.
- T003 / R7: the generated types are formatted by `db:types` (Prettier runs after generation)
  instead of being excluded from Prettier. Output is still deterministic.
- T009 (analysis finding U1): `db:check` loads `.env.local` then `.env` itself
  (`process.loadEnvFile`), matching Next.js precedence. `.env*.local` was added to `.gitignore`.
- T015: `supabase/migrations/.gitkeep` was dropped because the CLI warns about it; the first
  `supabase migration new` creates the folder.
- T016: covered by the `supabase/.gitignore` that `supabase init` generates (`.branches`, `.temp`).
- T017: Supabase CLI v3 changes. `db push` targets the local DB by default, so `db:push` passes
  `--remote="$SUPABASE_PROJECT_REF"`. `link` ignores `--password`. `gen types` no longer needs
  `--local`.
- Env file: the real settings live in `.env.local` (renamed from `.env` on 2026-11-24). Scripts
  still read `.env` as a fallback. Task texts above that mention `.env` refer to that file.
- T020: pending. Remote CLI commands need `npx supabase login` once per machine (access token).
